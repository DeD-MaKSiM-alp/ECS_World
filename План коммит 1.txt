Решение про старый прототип (Velocity / float)
Как в вашем же плане (стр. 167): либо заменить на задел под сетку, либо вынести черновик. Для коммита 1 разумно:

Вариант A (минимальный каркас): оставить одну пару компонентов как учебный пример совместимости с текущим main (например Position + Velocity), но уже разнесённые по файлам и с EntityId. Сеточные поля появятся в коммите 2.
Вариант B (строже к GDD): в коммите 1 только пустые или заглушечные компоненты без float-движения; main только создаёт мир и проверяет createEntity — больше кода в «examples/» или старый файл prototype_velocity.cpp не в сборке.
В плане ниже заложен вариант A как меньший скачок от текущего репо.

План по файлам и модулям (псевдокод структуры)
project_root/
  include/ecs/           // или src/ecs/ если всё из одной директории
    EntityId.h           // только тип id + константа «невалидный»
    Components.h         // только POD-структуры данных (Position, Velocity, позже остальное)
    World.h              // объявление World: поля + сигнатуры методов, без тела тяжёлых функций
  src/ecs/
    World.cpp            // реализации методов World (createEntity, add/get компонентов)
  include/systems/       // опционально уже в коммите 1
    MovementSystem.h     // объявление системы + метод update(World&)
  src/systems/
    MovementSystem.cpp   // реализация update
  main.cpp               // тонкий: создать World, одна сущность, один вызов update/tick, вывод в консоль
Правило зависимостей:

Components.h не включает World.h.
World.h включает EntityId, контейнеры, forward-declaration систем или не держит системы как члены — см. ниже.
MovementSystem.* включает World.h и Components.h (или только то, что нужно для итерации).
План по типам (псевдоязык)
EntityId

Ввести именованный тип (strong typedef / enum class / struct-обёртка — конкретика на C++ по вкусу).
Поля: внутреннее целое; константа Invalid (например 0), договор «новые id только через World».
Операции на первом этапе: сравнение на равенство, при необходимости приведение к «сырому» индексу только внутри World или для логов — чтобы системы не разбрасывали по коду сырые int.
Компоненты

Position — два поля с плавающей точкой (как сейчас) или заглушка под будущую сетку — зафиксировать в комментарии GDD, что для прототипа коммита 1 допустим float.
Velocity — аналогично.
Никаких методов с логикой внутри компонентов на коммите 1 — только данные.
План по World (псевдоязык)
Поля

Счётчик следующего id (nextEntity того же типа, что и внутренность EntityId).
Хранилища: ассоциативные контейнеры «ключ = EntityId или его сырой эквивалент, значение = компонент». Имена полей по смыслу: positions, velocities.
Системы:
Либо члены World (как сейчас) — быстро и явно;
Либо World::update / World::tick принимает снаружи вызываемые системы — слабее связность, но больше кода в main. Для коммита 1 достаточно оставить одну систему как член или один вызов свободной функции — главное, чтобы граница «мир вызывает системы» была одна.
Методы (минимум)

createEntity() → возвращает EntityId, увеличивает счётчик, не кладёт компоненты автоматически.
Для каждого компонента первого этапа: addX(EntityId, X), getX(EntityId) → указатель или optional на мутабельные данные; отсутствие ключа → «нет компонента».
Именование под будущее

Зарезервировать имя tick() как основной цикл симуляции (по GDD), а update() объявить устаревшим алиасом или сразу переименовать в tick() — чтобы коммит 4 не ломал все вызовы.
План по MovementSystem (псевдоязык)
Вход: ссылка на World.
Алгоритм: как сейчас — перебор всех сущностей с Velocity, для каждой — если есть Position, обновить координаты.
Не включать заголовки ввода-вывода и не знать про консоль.
План по main (псевдоязык)
Создать World.
EntityId e = world.createEntity().
Добавить позицию и скорость для e.
Вызвать world.tick() (или текущее имя).
Прочитать позицию и вывести в консоль для ручной проверки.
План по сборке
Если уже есть CMake/Makefile — добавить исходники World.cpp, MovementSystem.cpp.
Если одного .cpp канает на Windows — можно оставить один translation unit, но файлы физически разнести и подключать через #include реализаций (не идеал для больших проектов, но для коммита 1 допустимо как промежуточный шаг). Предпочтительнее сразу несколько .cpp и один исполняемый файл.
Что сознательно не делать в коммите 1 (чтобы не раздувать)
Нет Grid, нет moveEntity, нет порядка систем из GDD — это следующие коммиты.
Нет удаления сущностей и переиспользования id — можно запланировать TODO в коде или в плане коммита 5+.
Краткий чеклист «готово к коммиту 1»
Папки include / src (или эквивалент) согласованы с будущими системами.
EntityId + невалидное значение задокументированы.
World централизует создание сущностей и словари компонентов.
Компоненты — отдельные типы данных; система — отдельная единица компиляции или файла.
main доказывает, что проект собирается и поведение как у текущего прототипа (один тик, позиция меняется).
