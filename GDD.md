# Game Design Document (GDD) v0.3

---

# I. Концепция мира

## 1. Общая идея

Мир представляет собой **автономную пошаговую симуляцию**, которая:

- не зависит от игрока  
- может существовать без игрока  
- развивается по внутренним правилам  

Игрок:

- либо является одной из сущностей  
- либо выступает как внешний управляющий агент  

> Мир является первичным, игрок — вторичным

---

## 2. Основной принцип

> Мир не зависит от игрока как от источника существования и времени. При этом игрок может быть участником мира и своими действиями изменять состояние симуляции.

Игрок может:

- инициировать действия  
- ускорять изменения  

Но не является источником существования мира.

---

# II. Модель времени

## 3. Тики

Мир работает через дискретные шаги:

- 1 тик = 1 обновление состояния мира  

---

## 4. Типы тиков

1. **Тик действия**
   - возникает при действии игрока  

2. **Автотик**
   - происходит при бездействии игрока  

---

## 5. Принципы времени

- мир не останавливается без игрока  
- системы не знают о времени  
- системы работают только с тиками  

---

# III. Правила симуляции

## 6. Сущности

Все объекты мира — сущности:

- живые (NPC, животные)  
- неживые (еда, ресурсы)  
- статические (объекты среды)  

---

## 7. Потребности

На первом этапе реализуется:

- Hunger (голод)

Поведение:

- каждый тик голод увеличивается  
- при превышении порога запускается поиск еды  

---

## 8. Взаимодействия

Минимальное правило:

- если сущность находится в одной клетке с едой:
  - еда удаляется  
  - голод уменьшается  

---

# IV. Пространственная модель

## 9. Grid

Мир представлен в виде сетки:

- размер: 20x20  
- состоит из клеток  

---

## 10. Клетка (Cell)

Каждая клетка содержит:

```text
- entities: список entityId
```

Проходимость клетки на этапе 1 определяется не полем клетки, а компонентами сущностей в этой клетке (см. `Walkable` в §24 и правила в §12, §31).

---

## 11. Типы сущностей в клетке

Сущности делятся на:

- блокирующие  
- неблокирующие  

Правила:

- только одна блокирующая сущность в клетке  
- несколько неблокирующих допускаются  

---

## 12. Проходимость

На текущем этапе:

- по умолчанию все клетки проходимые  
- непроходимость может задаваться сущностью с компонентом `Walkable{value=false}` в клетке  

В будущем:

- появятся препятствия  
- появится стоимость перемещения  

---

# V. Поведение и AI

## 13. Принцип поведения

Поведение определяется **состоянием сущности**, а не скриптами.

Пример:

- голод → поиск еды → движение → взаимодействие  

---

## 14. Модель AI (этап 1)

Используется простая логика:

```text
if hunger > threshold:
    найти ближайшую еду
    установить цель движения
```

---

## 15. Выбор цели

Цель определяется как сущность:

- MoveTarget = targetEntityId  

Выбор:

- ближайшая еда по **Manhattan distance**  
- при нескольких единицах еды на **одинаковом** расстоянии выбирается сущность с **меньшим `entityId`** (детерминированный tie-break)

---

## 16. Принятие решений

AI выполняется каждый тик:

- анализирует состояние  
- при необходимости обновляет цель  

---

## 17. Обработка исчезновения цели

Если цель исчезла:

- MoveTarget удаляется  
- на следующем тике выполняется новый поиск  

### Сценарий: NPC и еда (прототип, этап 1)

На прототипе рассматривается **один NPC** и конкуренция нескольких агентов за одну еду **не специфицируется** — правила будут добавлены позже.

Пошагово:

```text
Пока голод ниже порога:
    NPC не получает целей от AISystem (или цели нет)

Когда голод > threshold:
    AISystem выбирает ближайшую еду (§15) и ставит MoveTarget

Пока еда не в той же клетке:
    MovementSystem по MoveTarget делает шаг (§18–21); за тик — только движение

Когда NPC в одной клетке с едой и нужно поесть:
    AISystem снимает MoveTarget и ставит InteractTarget на еду
    InteractionSystem за тик обрабатывает взаимодействие (еда удаляется, голод уменьшается)
```

Так соблюдается правило **одного активного действия за тик** (§42): в один тик либо шаг к еде, либо поедание, без смешения.

# VI. Перемещение

## 18. Модель движения

- движение происходит по клеткам  
- 1 шаг = 1 тик  

---

## 19. Поиск пути (этап 1)

Используется простая стратегия:

- движение в сторону цели  
- без обхода препятствий  

---

## 20. Условия движения

Сущность движется, пока:

- цель существует  
- цель не достигнута  

---

## 21. Остановка движения

Движение прекращается, если:

- достигнута цель  
- цель исчезла

# VIII. Техническая архитектура

## 27. World

World является центральной точкой управления:

- хранит сущности  
- хранит компоненты  
- содержит Grid  
- управляет системами  

---

## 28. Grid

Grid отвечает за:

- хранение клеток  
- хранение сущностей в клетках  

Grid не содержит логики.

---

## 29. Position

**Position (компонент)** — источник правды о координатах сущности:

```text
x, y
```

**Grid** — вспомогательный индекс: по клетке можно быстро получить список `entityId`. Логика перемещения и проверок опирается на компонент позиции; индекс должен **соответствовать** ему после любого изменения через `World.moveEntity` (или эквивалент).

---

## 30. Перемещение сущностей

Перемещение выполняется через World:

```text
World.moveEntity(entity, newPosition)
```

---

## 31. Проверка движения

World проверяет:

- границы карты  
- проходимость  
- блокирующие сущности  

---

## 32. Невозможность движения

Если движение невозможно:

- сущность остаётся на месте  

---

# XII. Game Loop и управление временем

## 38. Назначение Game Loop

Game Loop отвечает за выполнение приложения и управление ходом симуляции.

Game Loop не является частью мира. Он управляет тем, когда мир должен сделать следующий тик.

### Разделение ответственности

```text
Game:
- читает ввод игрока
- переводит ожидающее действие игрока в компоненты намерения на сущности игрока (не меняет Position напрямую)
- управляет паузой
- решает, когда выполнить тик (в т. ч. §46–47)
- вызывает World.tick()
- вызывает отображение мира

World:
- хранит состояние мира
- хранит сущности и компоненты
- содержит Grid
- выполняет системы

Systems:
- изменяют состояние мира через World

ConsoleRenderer:
- отображает текущее состояние мира
```

### Принцип

World не должен знать:

- откуда пришёл ввод
- какая клавиша была нажата
- сколько прошло реального времени
- как часто срабатывает автотик
- как мир отображается в консоли

---

## 39. Тик мира

Один тик — это один ограниченный шаг симуляции.

Тик не должен выполнять слишком много активных действий сразу. Это нужно, чтобы сохранить ощущение пошагового мира.

### Принцип

```text
1 тик = 1 шаг развития мира
```

За один тик сущность может выполнить только одно активное действие.

Примеры активных действий:

- сделать шаг
- взаимодействовать с объектом
- атаковать
- подобрать предмет

При этом фоновые изменения могут происходить каждый тик и не считаются активным действием.

Примеры фоновых изменений:

- рост голода
- рост усталости
- изменение температуры тела
- восстановление или ухудшение состояния

---

## 40. Типы систем

Системы делятся на несколько категорий.

### Фоновые системы

Фоновые системы изменяют состояние мира независимо от активного действия сущности.

Они выполняются каждый тик и не конфликтуют с движением или взаимодействием.

Примеры:

```text
HungerSystem
FatigueSystem
TemperatureSystem
RegenerationSystem
```

На первом этапе используется:

```text
HungerSystem
```

---

### Системы принятия решений

Системы принятия решений анализируют состояние сущности и определяют, что она хочет сделать.

Они не выполняют действие напрямую.

Пример:

```text
AISystem
```

AISystem может решить:

```text
если голод высокий и еды рядом нет → двигаться к еде
если голод высокий и еда в той же клетке → взаимодействовать с едой
```

---

### Исполнительные системы

Исполнительные системы выполняют активные действия сущности.

За один тик сущность может выполнить только одно активное действие.

Примеры:

```text
MovementSystem
InteractionSystem
```

Правило:

```text
MovementSystem и InteractionSystem не должны выполнять действие для одной и той же сущности в один и тот же тик.
```

---

## 41. Порядок обновления мира

Внутри одного тика системы выполняются в фиксированном порядке:

1. **Фоновые системы**  
   - HungerSystem  

2. **Системы принятия решений**  
   - AISystem  

3. **Исполнительные системы**  
   - MovementSystem  
   - InteractionSystem  

**Очистка:** отдельной `CleanupSystem` на первом этапе **нет**. Временные компоненты намерения и результата (`MoveTarget`, `InteractTarget` и т. п.) **снимает та система, которая их обработала** (или обновила состояние по итогу действия).

*(Идея «мини-таблицы»: позже, при росте числа систем, можно завести таблицу «система → читает компоненты → пишет компоненты» для порядка побочных эффектов. На этапе 1 достаточно списка выше.)*

---

## 42. Правило одного активного действия

Каждая сущность имеет ограничение:

```text
1 тик = максимум 1 активное действие
```

Если сущность в текущем тике двигается, она не может в этот же тик взаимодействовать.

Если сущность в текущем тике взаимодействует, она не может в этот же тик двигаться.

Пример:

```text
тик 1:
NPC сделал шаг к еде

тик 2:
NPC сделал ещё один шаг к еде

тик 3:
NPC оказался на клетке с едой

тик 4:
NPC съел еду
```

Это сохраняет пошаговость и делает поведение мира более читаемым.

---

## 43. Намерение действия

Система принятия решений не выполняет действие напрямую.

Она задаёт намерение действия через компоненты.

Примеры:

```text
MoveTarget — сущность хочет двигаться к цели
InteractTarget — сущность хочет взаимодействовать с целью
```

Исполнительные системы читают эти компоненты и выполняют только одно подходящее действие за тик.

---

## 44. Очистка состояния после действия

После выполнения активного действия временные компоненты действия могут быть удалены или обновлены.

Пример:

```text
если сущность дошла до еды:
    MoveTarget удаляется (как правило, системой движения или AISystem — по выбранной реализации)
    на следующем тике AISystem может установить InteractTarget
```

Пример:

```text
если сущность съела еду:
    InteractTarget удаляется
    Food удаляется
    Hunger уменьшается
```

---

## 45. Принцип пошаговости

Даже если несколько систем вызываются в одном тике, тик остаётся пошаговым, потому что:

- фоновые системы не считаются активным действием
- AI только принимает решение
- исполнительные системы ограничены одним активным действием на сущность
- движение и взаимодействие не выполняются одной сущностью в один и тот же тик

---

## 46. Автотик

Автотик срабатывает **только после бездействия игрока** (нет нового релевантного ввода в течение заданного окна — детали таймера в реализации). Пока игрок **активен**, продвижение симуляции идёт **только** от тиков, вызванных его действиями (см. §47), а не от отдельного «фонового» таймера автотика.

На первом этапе при бездействии:

```text
автотик происходит примерно 1 раз в секунду
```

### Назначение

Автотик нужен, чтобы мир не замирал, когда игрок ничего не нажимает.

### Будущее развитие

В будущем скорость автотика может быть настраиваемой:

```text
x0.5
x1
x2
x5
```

---

## 47. Тик от действия игрока

Пока игрок активен, **ход мира привязан к его действиям**: ввод инициирует следующий тик (если разрешён лимитом частоты). Частота таких тиков ограничена, чтобы нельзя было бесконтрольно ускорять симуляцию.

### Принцип

```text
действие игрока инициирует тик
но не чаще заданного лимита
```

На первом этапе можно использовать ограничение:

```text
не больше 5 тиков в секунду от действий игрока
```

### Итоговое правило времени

```text
один мир, один World.tick() за шаг цикла
пока игрок активен — тики от действий игрока (в пределах лимита)
когда игрок бездействует — тики по автотику (~1 раз в секунду)
```

---

## 48. Ввод игрока

Очередь команд игрока не используется.

Это сделано для того, чтобы игрок не терял контроль из-за накопившихся действий.

### Принцип

Если игрок нажимает несколько действий слишком быстро:

```text
сохраняется только последнее актуальное действие
```

Пример:

```text
игрок нажал W
затем быстро нажал A
ожидающим действием становится A
```

---

## 49. Ожидающее действие игрока

Если действие игрока получено, но тик пока запрещён ограничением частоты, действие не теряется.

Оно сохраняется как последнее ожидающее действие.

```text
pendingPlayerAction = последнее действие игрока
```

Когда следующий тик становится разрешённым, ожидающее действие **переводится в намерение** (§51) и затем участвует в `World.tick()`.

---

## 50. Приоритет отложенного ввода и порядок шага цикла

Перед вызовом `World.tick()` Game проверяет ожидающее действие игрока.

Если оно есть и тик разрешён:

```text
Game записывает намерение игрока в компоненты (не меняя Position напрямую)
затем вызывается World.tick()
```

**Автотик** (§46) наступает только в режиме бездействия. Если игрок простаивал, накопилось отложенное направление (например, W) и сработал автотик — сначала это действие превращается в намерение, затем выполняется один `World.tick()` (как в примере ниже). Два независимых «ускорителя» тиков за один проход цикла не суммируются: за итерацию — **не более одного** `World.tick()`.

### Пример

```text
игрок нажал W
тик сейчас временно запрещён лимитом частоты
действие W сохраняется в pending

игрок перестал нажимать клавиши — наступает бездействие
срабатывает автотик: сначала W → намерение игрока, затем World.tick()
```

---

## 51. Игрок как сущность

Игрок является обычной сущностью мира.

Для игрока используются компоненты:

```text
Position
Blocking
PlayerControlled
Hunger
```

### Принцип

Игрок подчиняется тем же правилам мира, что и другие сущности.

Отличие игрока от NPC:

```text
NPC: намерение задаёт AISystem (компоненты MoveTarget / InteractTarget)
игрок: намерение задаёт Game по вводу (компонент намерения движения и т. п.); исполняют те же MovementSystem / InteractionSystem
```

**Ввод не изменяет мир напрямую.** Game только переводит ввод в компонент намерения на сущности игрока. **MovementSystem** исполняет намерение движения; фактическое изменение **Position** и согласование **Grid** выполняет **World** (например, `World.moveEntity`).

---

## 52. Игрок и потребности

Игрок участвует в системе потребностей.

На первом этапе игрок имеет Hunger так же, как NPC.

### Принцип

HungerSystem не различает игрока и NPC.

```text
если у сущности есть Hunger,
то HungerSystem обновляет её каждый тик
```

## 53. Пауза

Пауза нужна для отладки.

В режиме паузы:

- **`World.tick()` не вызывается** — останавливаются все тики, включая фоновые (например, рост голода)
- автотики не происходят
- движение и прочие активные действия не выполняются
- состояние мира можно спокойно анализировать

### Принцип

```text
paused = true → мир не делает тики
```

В будущем может быть добавлен отладочный режим:

```text
Step one tick
```

## 54. Завершение прототипа

Основной цикл игры является бесконечным, пока работает приложение.

Для прототипа допускается техническая команда выхода, например:

```text
Q — завершить прототип
```

Это не является игровой механикой, а нужно только для удобства отладки.

## 55. Минимальное управление прототипа

На первом этапе используется консольное управление:

```text
W — движение вверх
A — движение влево
S — движение вниз
D — движение вправо
Space — пауза / продолжить
Q — завершить прототип
```

### Примечание

Q является технической командой прототипа, а не частью игровой системы.

## 56. Структура Game

Game является отдельной структурой, управляющей приложением.

```text
Game:
- содержит World
- содержит ConsoleRenderer
- хранит состояние паузы
- хранит последнее ожидающее действие игрока (pending)
- по разрешённому тику записывает намерение игрока в компоненты
- управляет главным циклом
```

### Принцип слабой связанности

```text
Game знает про World
World не знает про Game
World не знает про Input
World не знает про Renderer
```

## 57. Общая схема цикла

```text
while game is running:

    read input

    if input is pause:
        toggle pause

    if input is movement (или иной игровой ввод, влияющий на намерение):
        сохранить как pendingPlayerAction (только последнее)

    if not paused:
        если разрешён тик от ввода игрока (§47) ИЛИ сработал автотик при бездействии (§46):
            если есть pendingPlayerAction:
                Game записывает намерение игрока в компоненты сущности игрока
            world.tick()
            render world   # только после полного тика (§34)
```

За одну итерацию цикла — **не более одного** `world.tick()`. Пока игрок активен, продвижение идёт от его действий; автотик не параллелит частые нажатия (§46–47).

## 58. Ключевые правила Game Loop

- мир обновляется только через тик
- один тик выполняет ограниченный шаг симуляции; за проход цикла — один вызов `World.tick()`
- игрок не является источником существования мира
- при бездействии автотик поддерживает жизнь мира (~1 Гц); при активном вводе тики идут от действий игрока (с лимитом частоты)
- частота тиков от игрока ограничена (§47)
- очередь действий игрока не используется
- последнее действие игрока может ожидать ближайшего разрешённого тика; Game переводит его в намерение, не мутируя позицию напрямую
- World остаётся независимым от Input и Renderer
