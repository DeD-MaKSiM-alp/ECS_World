Блоки работ под коммиты (по GDD v0.3)

Ниже — логические границы коммитов: в каждом коммите что-то можно запустить или проверить (хотя бы вручную), а зависимости между частями минимальны.

Идея связности:  





World знает сущности, компоненты, сетку и вызывает системы в фиксированном порядке (§41).  



Системы не знают про клавиатуру и консоль — только про компоненты и методы World.  



Game решает когда тикать и переводит ввод в компоненты намерения игрока; не двигает сущность напрямую (§51).  



Renderer только читает состояние после World.tick() (§34).

Порядок коммитов сверху вниз — типичная последовательность разработки «от данных к поведению к оболочке».



Коммит 1 — Каркас ECS и границы модулей

Цель: зафиксировать структуру папок и минимальный слой «сущность = id, компоненты = данные отдельно».

Широко: ввести тип идентификатора сущности, центральный объект мира с хранилищами компонентов (как в вашем текущем [main.cpp](c:\IT\cursor_projects\ECS_Game\main.cpp), но осознанно под расширение). Решить, где живут заголовки (World, базовые типы), чтобы системы включали только то, что им нужно.

Зачем отдельным коммитом: это фундамент; дальше все фичи лягут на него без переписывания половины файла.



Коммит 2 — Сетка, клетка, позиция как источник правды

Цель: пространство GDD (§9–12, §29): Grid 20×20, клетка со списком id, Position в компоненте — источник правды, Grid — индекс.

Широко: операции «зарегистрировать сущность в клетке», «синхронизировать индекс с позицией». Без AI и без игрока — можно тестовой функцией расставить несколько сущностей и убедиться, что индекс совпадает с координатами.

Связность: Grid не содержит игровой логики (§28); только хранение.



Коммит 3 — Безопасное перемещение через World

Цель: §30–32: единая точка смены позиции — например World.moveEntity: границы, проходимость, одна блокирующая сущность на клетку.

Широко: любое движение в коде в будущем идёт только через этот API; обновляются и компонент, и индекс клеток.

Зачем отдельно: это контракт между всеми системами; ошибки здесь ломают всё остальное.



Коммит 4 — Компоненты первого этапа и заготовка систем по порядку

Цель: §24–26: описать данные Hunger, Food, Blocking, MoveTarget, InteractTarget, PlayerControlled и реализовать пустой или минимальный World.tick(), который вызывает системы строго в порядке: Hunger → AISystem → Movement → Interaction.

Широко: на этом шаге системы могут быть «заглушками» (например, Hunger только увеличивает счётчик), но порядок уже как в GDD.



Коммит 5 — HungerSystem

Цель: §7: каждый тик увеличивать голод у всех с Hunger; порог для «искать еду» можно хранить как константу или поле.

Связность: система не знает про карту целиком — только про сущности с нужным компонентом и доступ к World для чтения/записи компонентов.



Коммит 6 — AISystem (NPC)

Цель: §14–17, §15: при голоде выше порога — поиск ближайшей еды (Manhattan, tie-break по меньшему entityId), выставление MoveTarget; в одной клетке с едой — снять движение к цели и выставить InteractTarget (как в сценарии под §17).

Широко: один NPC в прототипе — достаточно; конкуренцию не моделируем (как в GDD).



Коммит 7 — MovementSystem

Цель: §18–21, §19: шаг по направлению к цели без A*; один шаг за тик; вызов только World.moveEntity.

Связность: не читает клавиатуру; работает и для NPC, и позже для игрока через те же компоненты намерения.



Коммит 8 — InteractionSystem

Цель: §8: та же клетка, что и еда — съесть, убрать еду, уменьшить голод; снять InteractTarget там, где нужно.

Широко: удаление сущности-еды и обновление Grid — через World, чтобы индекс не разъехался.



Коммит 9 — Консольный рендер

Цель: §33–34: отрисовка сетки символами после полного тика; без логики симуляции.

Связность: Renderer получает только чтение состояния (или тонкий API «что рисовать в клетке»), не вызывает системы.



Коммит 10 — минимальный Game + цикл без реального ввода

Цель: §38, §57 в упрощении: объект Game держит World и Renderer; в цикле при не-паузе вызывается World.tick() и рендер. Ввод можно временно игнорировать или подставить фиктивный «один тик».

Зачем: проверить, что «один мир — один tick() за итерацию» уже соблюдается до усложнения таймингов.



Коммит 11 — Сущность игрока и намерение из Game

Цель: §51: игрок с Position, Blocking, PlayerControlled, Hunger; Game по «заглушке» или тестовому сценарию записывает компонент намерения (направление шага), MovementSystem исполняет так же, как для NPC.

Ключевой момент для новичка: клавиатуры ещё может не быть — важно не менять Position из Game напрямую.



Коммит 12 — Ввод с клавиатуры, pending, лимит 5 тиков/с

Цель: §48–50, §47: последнее действие вместо очереди; отложенное действие; ограничение частоты тиков от ввода.

Широко: Game читает ввод, кладёт pending, при разрешённом тике мапит в компонент намерения, затем World.tick().



Коммит 13 — Автотик при бездействии (~1 Гц)

Цель: §46: пока есть активный ввод — тики от действий игрока; после тишины — периодический тик; за проход цикла по-прежнему не больше одного World.tick() (§50, §58).

Широко: таймер «не было ввода N мс» + срабатывание автотика; совместимость с pending (пример из §50).



Коммит 14 — Пауза и выход Q

Цель: §53–55: при паузе не вызывать World.tick() вообще; Space переключает паузу; Q завершает приложение.



Как читать новичку





Коммиты 1–3 — «где всё лежит и как не сломать карту».  



4–8 — «мир сам живёт»: голод, NPC, ходьба, еда.  



9 — «мы это видим».  



10–14 — «игрок и время»: без лишней связи Input с системами.
